# Accessible technical documentation

State the decision, outcome, or action readers need near the top. Use the project's domain terms and define unfamiliar terms where readers first need them. Use short, concrete sentences and descriptive headings. Preserve technical precision, code identifiers, decisions, and constraints when simplifying wording.

## Choose a format that fits the content

- Use bullets for independent options, responsibilities, or requirements. Start each item with its subject and keep comparable items parallel.
- Use numbered lists for procedures or other sequences where order matters.
- Use tables for lookups and comparisons with shared columns. Give every column a clear heading. Keep cells short, avoid merged cells, and put long explanations in prose. Prefer bullets when a table would be difficult to read on a narrow screen.
- Use diagrams for flows, boundaries, dependencies, and relationships when the connections matter. Use the repository's supported format. Label nodes and explain what arrows mean. Give the diagram a short text equivalent that communicates the same relationships without rendering it. Use labels and structure for meaning so readers can follow it without color.

## Check the result

Read the headings, list labels, and table headers on their own. They should communicate the document's structure. Check diagrams for ambiguous arrow directions, unexplained abbreviations, and color-only cues. Use descriptive link text and confirm links resolve. Check a rendered preview when available, especially for wide tables and diagrams. Preserve the review history and scope when revising an existing decision.
